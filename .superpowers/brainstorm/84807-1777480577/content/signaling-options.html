Choose The Signaling Shape

WebRTC media is peer-to-peer, but the two browsers still need a rendezvous channel for offer, answer, and ICE candidates.

A. Manual copy / paste
Create offer JSON
copy to other browser
Paste answer JSON

No backend

Fastest and most transparent for learning/debugging. Awkward UX, especially with trickle ICE.

B. Next.js room mailbox
Browser A
POST / poll room events
Browser B

In-app signaling

Simple room link and no separate server. Good for local/dev prototype; production/serverless persistence needs care.

C. WebSocket signaling server
Browser A
WS room
Browser B

Real-time signaling

Best meeting-like behavior. Requires a running Node/WebSocket service separate from normal Vercel-style Next routes.

My recommendation

  • Use B for the first WebFastTry-native prototype.
  • Design signaling behind a small interface so C can replace it later.
  • Keep A as an optional debug/export panel if we want deep protocol visibility.

Main constraint

  • Two real browsers need some shared rendezvous state unless users manually pass JSON.
  • Vercel/serverless is not a natural WebSocket host.
  • In-memory rooms reset on dev server restart and do not scale across instances.
