Architecture Approach Options

All options build a pure WebRTC two-person meeting with WebSocket signaling, configurable ICE, collaboration tools, and media processing.

A. Single page prototype
page.tsx owns UI, WebRTC, media, signaling
small ws server

Fastest demo

Lowest initial overhead, but processor, stats, chat, reconnect, and share logic will quickly crowd the page.

B. Feature module with engines
meeting controller
signaling client
peer engine
media manager
processor manager
stats/log stores
independent ws signaling server

Recommended

Clear boundaries for future needs while still lightweight enough for WebFastTry. Best fit for your “prototype now, expand later” goal.

C. Package-style meeting core
meeting-core library
app shell imports core
signaling server package
processor plugin package

Most reusable

Strong long-term separation, but more ceremony than this repo currently uses and slower to get the first working meeting.

Why B fits

  • Keeps WebRTC, signaling, media capture, processors, stats, chat, and logs independently testable.
  • Leaves room for WebSocket deployment, TURN config, ML processors, and recording later.
  • Matches WebFastTry: a feature page plus a focused feature folder, without overbuilding a package ecosystem.

Trade-offs

  • More files than a demo page.
  • Needs a small state/controller layer so UI does not directly orchestrate all WebRTC operations.
  • Requires careful lifecycle cleanup for tracks, peer connection, processors, and WebSocket sessions.
